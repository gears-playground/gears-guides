Contract

Purpose
Translate scoped product work and research evidence into buildable specifications — interaction, visual, system, and any other discipline the work requires. Design owns how the thing works and what it looks like, and owns proving those choices before engineering commits to them.
Input
A UX Request and Product Brief from Product. Evidence from Research. Existing design system rules and prior sprint summaries.
Output
A Design Sprint Summary, a validated prototype, and a handoff package engineering can implement from. Design decisions are recorded with their rationale, the alternatives rejected, and how each held up under validation.

Tenets

Design runs against a fixed, ordered list of tenets. Each is a decision criterion with a validation question attached. Order is meaningful — when two tenets conflict, the higher-priority one wins. A design that excels against one tenet but fails another needs refinement, not a tradeoff argument.

Defining this list is part of standing up the Design gear. The list below is one instance of it.

Instance These six are khaos-studio's, written for professional film and television tooling. The practice transfers; these specific tenets do not.

  1. Establish customer trust

    Does this design choice build or maintain user trust?

  2. Keep everyone informed

    Does this maintain clear information flow between team members?

  3. Design for collaboration

    Does this enhance team collaboration?

  4. Support professionals

    Does this support professional work practices?

  5. Inform creative work

    Does this help users make informed creative decisions?

  6. Make it effortless

    Have we made this as effortless as possible?

Citing evidence

Design artifacts that cite research use Markdown footnote syntax [^N] in body prose, with definitions resolved at the end of the document and research atom IDs living only in those definitions. Footnote IDs are scoped to the artifact.

Procedure

Design runs at two levels. The gear has six stages. Stage 4 expands into a six-phase sprint that moves from low to high fidelity.

  1. Design request submission

    Task Using the product specification as a foundation, open a design request covering overview, goals, details of the improvement, supporting research, expected impact, and timeline.

    Expected result A complete design request.

    Prerequisites to advance The request is approved, with clear objectives and success criteria.

  2. Generate sprint plan

    Task Assign a designer, schedule the kickoff, and prepare a brainstorm surface framing the problem space, the tenets, foundational research, and an empty customer journey framework.

    Expected result A sprint plan with confirmed team and timeline, and a prepared brainstorm board.

    Prerequisites to advance The plan is recorded in the design backlog with assigned resources, and the board holds the research materials and empty frameworks.

  3. Sprint kickoff

    Task Review the request and confirm objectives. Develop design prompts as How-Might-We statements. Brainstorm against goals and journey pain points, then synthesize: group concepts, name themes, map solutions to touchpoints, and select what proceeds to wireframing.

    Expected result A documented customer journey with pain points, categorized concepts mapped to it, and a prioritized list for wireframing.

    Prerequisites to advance Team consensus on prioritized solutions, validated against the request's goals, user needs, technical feasibility, and journey pain points.

  4. Sprint execution

    Task Run the six sprint phases, iterating on feedback at each fidelity level.

    Sprint phases
    1. Brainstorm (Lo-Fi) — ideate, then synthesize into a curated set
    2. Interface exploration (Lo-Fi) — competitor analysis, information architecture, first concepts
    3. Interaction design (Mid-Fi) — digital wireframes communicating the architecture
    4. Conceptual prototype (Mid-Fi) — usable prototype aligned to the customer journey
    5. Visual prototype (Hi-Fi) — the testable, buildable representation
    6. Remote research — usability testing against the prototype

    Each phase declares its own hypothesis, goals, activities, expected artifacts, prerequisites to advance, and participants.

    Expected result Completed iterations at each fidelity level, usability testing results, iteration documentation, and final design proposals.

    Prerequisites to advance Each fidelity level reviewed and approved, usability testing complete, technical feasibility confirmed, design system compliance verified.

  5. Sprint conclusion

    Task Write the Design Sprint Summary and close the tracking record.

    Expected result A summary capturing outcome against objective, key design decisions with rationale and rejected alternatives, research and learning, prototype overview, design system impact, customer journeys, open questions and risks, and cross-references.

    Prerequisites to advance The summary is complete and stored where sprint summaries live.

  6. Handoff

    Task Prepare the design handoff package for engineering.

    Expected result Engineering-ready designs.

    Prerequisites to advance Designs approved and technical feasibility confirmed.

Instance The source procedure names specific tools and locations — a FigJam board, a GitHub project view, a "Design Hub" repository, a Design Tracking issue. Those are stripped here. Substitute your own shared brainstorm surface, backlog, and system of record.

Intake

Design's intake procedure is stage 1: a design request opened against an approved product specification, carrying overview, goals, details, supporting research, expected impact, and timeline. It is accepted when objectives and success criteria are clear.

Unlike Product, Design's intake procedure is not formalized as a sub-gear. It is a single gated stage.

Partial Design's intake procedure has no published article. What appears above is extracted from the gear procedure, not from a dedicated source.

Handoffs

Design → DevelopmentHandoff package, plus the Design Sprint SummaryDesigns are approved and technical feasibility is confirmed.
Design → ProductDesign Sprint SummaryOutcomes are stated against the objectives the brief set.

Because the gears are non-linear, a handoff is legal whenever its readiness condition holds. Design can hand a prototype to Research mid-sprint and take findings back without leaving the gear.

Operators

A sprint runs with a facilitator, a designer, and named participants from product, engineering, and any function the work touches. Judgment calls belong to people: which concepts proceed, whether a tenet is satisfied, whether the prototype represents the journey honestly. Agents draft the brief, sequence the plan, prepare the discovery board, run desk research, and write the summary.

Templates

Templates fix the shape of each artifact. Skills execute the gear — they are how Design moves to a new organization without carrying the original repository with it.

Templates

  • Design Sprint Plan — sprint overview, scope, success criteria, milestones, then one block per phase
  • Design Sprint Summary — metadata, outcome against objective, key design decisions, research and learning, prototype overview, design system impact, customer journeys, open questions and risks, cross-references

Skills

  • design-brief — turns a UX request into a structured brief
  • design-workshop-facilitator — builds the discovery board for phase 1
  • design-plan — turns a brief plus discovery into a milestone-gated sprint plan
  • design-report — turns a completed sprint into the summary

Instance Templates and the design-brief skill currently live in the khaos-studio Design repository. Portable copies are not yet published here.
