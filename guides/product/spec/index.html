Contract

Purpose
Convert raw signal into scoped, prioritized, evidence-backed work, and observe whether the work that shipped delivered the value it claimed. Product owns scope, priority, and the question of whether to build at all.
Input
Raw signal from any source — feature requests, bug reports, partner asks, internal observation. Evidence from Research. Specifications from Design. Outcome data from shipped software.
Output
Product Brief, User Stories, UX Request, Research Intake Request, PRD. Each is a legal input to at least one other gear.

Gear train

Product is the one gear that does not operate as a single workflow. It runs as a train of three sub-gears. Each completes its rotation before the next begins.

  1. Intake — captures, screens, and routes ideas.

    Phases: Capture → Screen → Route. Documented at product.gears.run/intake.

  2. Manage — coordinates cross-functional work at variable depths.

    Depth varies with the work: some items need a brief only, others run the full artifact chain through validation and a PRD.

  3. Observe — measures outcomes and confirms value was delivered.

    Observe closes the loop by feeding outcome data back in as new signal at Capture.

Unsourced Manage and Observe have no published procedure. The descriptions above are the full extent of what the source material defines. Their sub-pages are not yet written.

Citing evidence

Any artifact that cites research uses Markdown footnote syntax [^N] in body prose, with definitions resolved at the end of the document. Research atom IDs live in the footnote definitions, never in body prose. Footnote IDs are scoped to the artifact — [^1] in a UX Request and [^1] in the Design Brief it produces are independent.

Procedure

Each step names its task, the result that counts as done, and what must be true before the work advances.

  1. Capture

    Task Record the signal in one canonical place, with enough structure to be screened.

    Expected result A normalized intake item with source, description, and requester.

    Prerequisites to advance The item is not a duplicate of an existing one.

  2. Screen

    Task Decide whether the item enters the system at all.

    Expected result Accepted, rejected, or deferred, with the reason recorded.

    Prerequisites to advance An accept decision, and a stated problem the item addresses.

  3. Route

    Task Send the accepted item to the gear that can act on it.

    Expected result The item carries a destination gear and the artifact that will open work there — Research Intake Request, UX Request, or direct to Manage.

    Prerequisites to advance The destination gear's intake procedure accepts the artifact.

  4. Brief

    Task Write the Product Brief: problem, user need, success metrics, scope boundaries, stakeholders, and what still needs validating.

    Expected result A Product Brief that states what and why, and names its open questions.

    Prerequisites to advance Stakeholder alignment on the problem and the success metrics.

  5. Discover

    Task Turn the brief into User Stories with acceptance criteria. Open a Research Intake Request for anything the brief could not answer.

    Expected result User Stories sufficient for Design and Development to explore against.

    Prerequisites to advance Every open question from the brief is either answered or explicitly deferred.

  6. Validate

    Task Test the proposed solution against evidence from Research and specifications from Design.

    Expected result A validated concept, with the evidence cited.

    Prerequisites to advance Success metrics are measurable and a baseline exists.

  7. Specify

    Task Write the PRD: detailed requirements, validated designs and flows, technical considerations, edge cases, constraints.

    Expected result A PRD an engineer can build from without asking what was meant.

    Prerequisites to advance Engineering has estimated effort against the validated design.

  8. Observe

    Task Measure the shipped work against the success metrics named in the brief.

    Expected result A result per metric — met, missed, or still pending measurement — with evidence.

    Prerequisites to advance None. Observe emits new signal into Capture.

Draft Steps 1–3 follow the published Intake phases. Steps 4–8 are reconstructed from the artifact flow, not from a published Manage or Observe procedure. Confirm before treating them as specification.

Intake

Every gear has an intake procedure — the front door through which work enters it. Product is the only gear whose intake procedure is formalized as a sub-gear, with its own phases and its own page.

Product's intake procedure is the Intake sub-gear, documented at product.gears.run/intake.

Intake, capitalized, means Product's sub-gear. An intake procedure, lowercase, is the thing every gear has. Research, Design, and Development each have one; none is a sub-gear.

Research → ProductResearch findings, cited by atom IDFindings answer a question the brief raised.
Design → ProductDesign specificationsSpecifications are concrete enough to estimate against.
Development → ProductShipped software and outcome dataThe metric named in the brief can be measured.

Because the gears are non-linear, a handoff is legal whenever its readiness condition holds. Nothing requires the gears to run in order.

Operators

Product runs with a human owning scope and priority decisions, and agents producing first drafts of artifacts. The screen decision, the scope boundary, and the prioritization are human calls. Draft generation, evidence assembly, and consistency checking are agent work.

Instance In the khaos-studio implementation, PRD generation runs through GitHub Actions triggered on request approval, with structured YAML prompt templates and persona matching. That automation is one way to run this gear, not part of the framework.

Templates

Templates fix the shape of each artifact. Skills execute the gear — they are how Product moves to a new organization without carrying the original repository with it.

Templates

  • product-brief.md — Product Brief
  • user-stories.md — User Stories
  • product-requirements.yaml — PRD
  • ux-request.yaml — UX Request
  • research-intake-request.yaml — Research Intake Request

Skills

  • prd-v1-generator — drafts a PRD from an approved request
  • user-scenario-generator — drafts user scenarios from a brief

Instance Both templates and skills currently live in the khaos-studio Product repository. Portable copies are not yet published here.
